# Блок 1. QA и UX-аудит скиллы для Claude: агент проходит веб-UI как пользователь

Дата исследования: 2026-10-31. Все репозитории клонированы с `--depth 1` в локальный клон (код не исполнялся). Для каждого утверждения указан URL; пути к файлам даны относительно корня соответствующего репозитория, коммит указан в карточке.

Контекст заказчика: стартапы с генеративным UI внутри чата (карточки, кнопки, слайдеры, формы прямо в ленте сообщений, ответ LLM приходит потоком), плюс обычные многостраничные приложения. Скиллы собираются через собственный генератор lab-forge, поэтому важны лицензия и модульность.

## TL;DR

- Готового скилла, который умеет нормально тестировать **генеративный UI в чате** (ждать окончания стрима, проверять карточки, отрисованные из tool-call, кнопки Approve/Deny, повторную генерацию), **не найдено** ни в одном из 17 просмотренных репозиториев. Ближе всех подходят jezweb `ux-audit` (каталог «тихих отказов» в чат-интерфейсах на `@ai-sdk/react`) и движок vercel `agent-browser` (прямо предупреждает, что `networkidle` зависает на SSE/WebSocket, и предлагает `wait --fn`). Этот модуль придётся дописывать самим.
- Почти все «dogfood»-скиллы происходят от одного предка: vercel-labs/agent-browser `dogfood` (Apache-2.0). Hermes, AojdevStudio и pm-pilot — его форки или пересказы под другой браузерный движок.
- По глубине UX-аудита сильнее всех jezweb `ux-audit` (MIT): блокировка персоны, манифест взаимодействий как доказательство, round-trip A→B→A, подсчёт кликов, самокритика через сабагента. Минусы: тяжёлый (~70k токенов, если грузить всё) и местами сам себе противоречит.
- Персоны лучше всего проработаны у ncklrs `claude-chrome-user-testing` (MIT, 25 персон в JSON с таймингами и триггерами фрустрации) и у hermes `adversarial-ux-test` (MIT, «злой пользователь» плюс прагматический фильтр). Ни один из них не запускает персоны по-настоящему параллельно: «multi-persona» в обоих случаях означает последовательные прогоны в одной сессии.
- Движки браузера, на которых стоит строить свой скилл: **Playwright CLI** (Apache-2.0, самый экономный по токенам, снапшоты пишутся в файл), **agent-browser** (Apache-2.0, удобные `wait --text/--fn`, `--annotate`, видео, облачные провайдеры), **Chrome DevTools MCP** (Apache-2.0, `wait_for` по нескольким текстам, ожидание стабильного DOM после каждого действия, трассы производительности).
- borghei `qa-browser-automation` распространяется под **MIT + Commons Clause** (продавать нельзя, sublicense вырезан). В lab-forge можно переносить только пересказ идей с атрибуцией. В формуле health score там ошибка: P0 снимает 5.4 балла, а не заявленные 30.

## Карточки решений

### 1. vercel-labs/agent-browser — `dogfood`

- **Репо:** https://github.com/vercel-labs/agent-browser (≈45k★), коммит `5868f7c` от 2026-10-30. Файлы: `skill-data/dogfood/SKILL.md`, `references/issue-taxonomy.md`, `templates/dogfood-report-template.md`. Скилл отдаётся командой CLI `agent-browser skills get dogfood`; файл `skills/agent-browser/SKILL.md` служит только заглушкой-указателем.
- **Лицензия:** Apache-2.0 (`LICENSE`).
- **Workflow (6 шагов):** Initialize → Authenticate → Orient → Explore → Document → Wrap up.
  - Нужен только URL, остальное берётся по умолчанию, лишних вопросов агент не задаёт.
  - На каждой странице: `snapshot -i`, скриншот `--annotate`, затем `errors` и `console`.
  - Каждая находка документируется сразу при обнаружении, а не в конце.
  - Цель — 5–10 хорошо доказанных проблем, после чего пересчитываются итоги.
- **Как водит браузер:** реальный Chrome/Chromium через CDP, Rust-CLI с демоном. Страницу агент «видит» как AX-снапшот с компактными ссылками `@eN`. Скриншоты служат доказательством; `--annotate` нумерует элементы под мультимодальные модели. Есть видео (`record start/stop`), `state save` для авторизации, именованные сессии (`--session`), облачные провайдеры (AgentCore, Vercel Sandbox) (README.md: разделы Sessions, Wait).
- **Ожидание динамики (важно для чата):** в core-скилле есть отдельный раздел «Waiting (read this)» (`skill-data/core/SKILL.md:200-224`). Там `wait --text`, `wait --fn "<JS-условие>"`, `wait "#spinner" --state hidden` и прямое предупреждение: `networkidle` не годится для SSE, WebSocket и long-polling, потому что сеть никогда не затихает. Для стриминговых чатов это ключевое.
- **Отчёт:** `ISSUE-NNN`, severity critical/high/medium/low, 7 категорий (visual, functional, ux, content, performance, console, accessibility), URL, видео, нумерованные шаги со скриншотом на каждом шаге. Статичные баги (опечатка, обрезанный текст) оформляются одним аннотированным скриншотом без видео. Перед сбором доказательств баг нужно воспроизвести хотя бы один раз повторно.
- **Персоны:** нет.
- **Масштаб:** одна сессия на один прогон. Параллельность возможна через несколько `--session` и `--pin-tab`, но сам скилл это не оркестрирует.
- **Что переиспользовать (пересказ):**
  - «Repro-first»: находка фиксируется сразу и с доказательствами, без пачки в конце.
  - Уровень доказательств подбирается под тип бага: интерактивный баг — видео плюс скриншот на каждом шаге, статичный — один кадр.
  - Повторное воспроизведение перед записью.
  - Запрет читать исходники тестируемого приложения: только то, что видно в браузере.
  - Видео в человеческом темпе: паузы между действиями, посимвольный ввод.
  - Лимит 5–10 качественных находок вместо 50 сомнительных.
  - Чеклист на каждой странице: визуальный скан → интерактивные элементы → формы → навигация → состояния (empty/loading/error/overflow) → консоль → responsive → границы авторизации.

### 2. jezweb/claude-skills — `ux-audit`

- **Репо:** https://github.com/jezweb/claude-skills (≈1.1k★), коммит `1260fa7` от 2026-10-09. Файлы: `plugins/dev-tools/skills/ux-audit/SKILL.md` (473 строки) + 22 файла в `references/` + `plugins/dev-tools/commands/ux-audit.md`. Всего ≈283 КБ, то есть ≈70k токенов при полной загрузке.
- **Лицензия:** MIT, © 2025 Jeremy Dawes (`LICENSE`).
- **Workflow (7 фаз):** Pre-flight → Discovery → Walkthrough → Polish → Stress → Verdict → Fix-and-verify.
  - **Pre-flight:** пять стоп-гейтов. Блокировка персоны, выбор браузерного тула, поиск URL, вьюпорт 1440×900, проверка того, что работают скриншот, консоль, сеть и селектор.
  - **Discovery:** карта сайта плюс «нити» — 3–5 реальных ежедневных задач.
  - **Walkthrough:** обязательный Interaction Manifest; проход нитей от точки входа; объёмы списков 0/1/100/1000+; мульти-панели; взгляд нового пользователя; smoke-проверка живых взаимодействий; round-trip; responsive; истечение сессии.
  - **Polish:** визуальные «AI-tells», axe-core, бюджет производительности.
  - **Stress:** 11 сценариев плюс 16 стресс-рецептов.
  - **Verdict:** Pass / Conditional / Fail / Incomplete.
  - **Fix-and-verify:** чинит и заново проходит затронутый участок.
- **Как водит браузер:** Claude in Chrome MCP для приложений с логином (реальная залогиненная сессия), Playwright MCP или playwright-cli для публичных сайтов. Если подходящего тула нет, аудит останавливается, а не продолжается молча без авторизации.
- **Ожидание динамики:** только фиксированные таймауты: «посмотреть следующее состояние 2 с», toast за 5 с, input очищен за 1 с. Общей стратегии ожидания нет. Для чатов есть полезное: рецепт манифеста для страницы-разговора (ввёл → отправил → поле очищено → сообщение добавлено); каталог «тихих отказов» — Approve/Deny на карточках tool-call, `sendAutomaticallyWhen` в `@ai-sdk/react`, двойная вставка mention; разговор на 200+ сообщений; `aria-live`. Чего нет: ожидания конца стрима, кнопок stop/regenerate, частичных ответов.
- **Отчёт:** самый сильный из всех.
  - Блок вердикта: персона, покрытие маршрутов N/M, скоркарта жёстких гейтов (любая ошибка в консоли = Critical, 5xx = Critical, LCP > 4 с и т. д.), время по фазам.
  - Поля находки: ID, слой (Architecture/Interaction/Visual/Feedback/Delight), severity, поверхность (маршрут + вьюпорт), персона, шаги, Observed/Expected, доказательства, предполагаемое место в коде `file:line`, «минимальный патч».
  - Top-5, дорожная карта Quick wins / Structural / Polish.
  - Правило «нет PASS без артефакта».
  - Дедупликация через свежего сабагента с метками KEEP/GENERIC/DUPLICATE.
- **Персоны:** persona-lock. Персона берётся из аргумента, из файла проекта или по одному вопросу пользователю, после чего записывается в `.jez/audit-personas/`. Шаблон: кто, цели, ограничения (например, «максимум 2 клика»), триггеры боли, «как аудировать от лица этой персоны». 6 персон по умолчанию плюс наборы по типу приложения. Отслеживается дрейф: фраза «разработчик бы…» запускает повторный проход.
- **Масштаб:** «persona-overload» — N **последовательных** аудитов с разными персонами, затем сабагент-синтезатор. Автор приводит свой результат: 4 прохода дали 56 находок. Для аудитов дольше 30 минут предусмотрен супервизор `/loop 15m`. Браузер должна вести основная сессия, а не сабагент.
- **Слабые места:** внутренние противоречия. Шаблон отчёта использует формулировку «Suggested fix», хотя дисциплина вывода её запрещает; где-то упоминаются 9 сценариев, а их 11; severity фокус-ловушки расходится между файлами. Сильная привязка к стеку автора: `.jez/`, React/TanStack, macOS `sips`, axe с CDN. Таймстемпы, по которым проверяется сам аудит, агент сообщает о себе сам.
- **Что переиспользовать (пересказ):**
  - **Persona-lock** с детектором дрейфа и отдельный обязательный «взгляд новичка».
  - **Interaction Manifest:** журнал действий по типам (TYPE, PICK, SUBMIT, OPEN, ASSERT, CONSOLE, NETWORK), минимум 6 на маршрут. Если в журнале одни READ, агент «листает», а не тестирует.
  - **Метрики эффективности потока:** число кликов против оценки оптимума, точки решения, тупики, лишние шаги. «Каждое колебание — это находка». Это прямой ответ на запрос «найти лишние шаги».
  - **5 вопросов нити** на каждом шаге: где начать? подсказывает ли интерфейс следующий шаг? виден ли прогресс? можно ли продолжить позже? понятен ли конец?
  - **Round-trip A→B→A:** изменить данные на B, вернуться видимой кнопкой «назад» без перезагрузки и проверить, обновилось ли A. Если помогает только reload, это и есть баг.
  - **Live-interaction smoke:** клик → смотреть сеть → смотреть DOM. Если ничего не поменялось, это баг. Отдельно форсированный 500-й ответ для проверки отката оптимистичного UI.
  - **Data seasoning:** проверять приложение на данных «день 0/1/7/30».
  - **Allowlist шума консоли** с показом и сырых, и отфильтрованных счётчиков.
  - **«Audit the audit»:** если доказательств мало, вердикт принудительно становится Incomplete.
  - **Killer-flow:** каждую найденную критичную проблему превращать в Playwright-тест на 10–30 строк.

### 3. borghei/Claude-Skills — `qa-browser-automation`

**Внимание: лицензия MIT + Commons Clause. Ниже только пересказ, текст не копируется.**

- **Репо:** https://github.com/borghei/Claude-Skills (≈1k★), коммит `2c12c7e` от 2026-10-23. Файлы: `engineering/qa-browser-automation/` (SKILL.md, 3 references, 2 assets, 4 Python-скрипта). `.codex/skills/qa-browser-automation` — симлинк на тот же каталог.
- **Лицензия:** Commons Clause v1.0 поверх модифицированного MIT. Из гранта убраны «sublicense» и «sell». Нельзя продавать продукт или услугу, ценность которых в основном составляет это ПО; уведомление обязано сопровождать все копии. Для открытого `product-layer` под MIT это значит: только идеи и атрибуция в CREDITS.md.
- **Workflow:** сначала уточнения (цель и логин, уровень тестирования, автономия фиксов, уровень WCAG), затем 11 фаз.
  - Остановка при «грязном» git, карта страниц, консоль и сеть (4xx/5xx), формы (валидный/пустой/граничный ввод).
  - Пять состояний UI, и для каждого взаимодействия «4 теневых пути»: счастливый, nil, пустой, ошибка upstream.
  - Брейкпоинты 320–1920, тач-таргеты 44 px, заголовки безопасности.
  - Классификация P0–P4 по 10 категориям; автофикс P3/P4, а для P0–P2 сначала спрашивает.
  - Повторная проверка, базовая линия, отчёт.
  - Уровни глубины: Quick 30 с / Standard 2–5 мин / Deep 10–20 мин / Exhaustive 30+ мин.
- **Как водит браузер:** целиком через внешний Claude in Chrome MCP. Python-скрипты браузер не открывают: это скоринг здоровья, статический a11y-аудит HTML, «визуальная регрессия» по SHA-256 (без пиксельного сравнения) и генератор отчёта.
- **Ожидание динамики:** практически не описано. Есть только совет после SPA-навигации подождать и перечитать страницу.
- **Отчёт:** JSON-схема находки (severity, category, steps_to_reproduce, expected, actual) и markdown-шаблон с executive summary, дашбордом оценки, P0–P4, a11y и CWV. «Нет находки без скриншота».
- **Ошибка:** в `qa_health_scorer.py` штраф умножается на вес категории, поэтому P0 в Functional снимает 30 × 0.18 = 5.4 балла вместо заявленных 30. Приложение с P0 может получить оценку A.
- **Персоны и масштаб:** нет.

### 4. NousResearch/hermes-agent — `dogfood` и `adversarial-ux-test`

- **Стоимость (из документации):** v2-агент ≈ $0.01 за задачу + $0.006 за шаг, браузер $0.02 в час (`skills/qa/SKILL.md:32`, `references/browser-use-v2.md:8-11`). Это своя модель Browser Use, токены Claude не тратятся. 100 прогонов по 40 шагов ≈ $26, 1000 ≈ $260 плюс браузерные часы. Есть повтор сохранённого прогона без LLM.
- **Минусы:** привязка к облаку и кредитам Browser Use, хрупкий туннель, бедный отчёт, одна оценка прячет отдельные баги. Сам скилл признаёт, что самооценке агента верить нельзя.
- **Что переиспользовать:**
  - Независимый судья с ground truth успеха, перекрывающий самооценку агента.
  - Агрегирование по самому слабому критическому пути.
  - «Не доверяй чистому скриншоту»: всегда тянуть события консоли и сети.
  - Список артефактов окружения, которые не считаются багами.
  - Обязательный teardown.
  - Дорогие и разрушительные действия выполнять минимально.

### 16. browserbase/skills — `ui-test` (+ `agent-experience`)

- **Репо:** https://github.com/browserbase/skills (≈3.7k★), коммит `6811ca3`. В корне LICENSE нет; у каждого из 18 скиллов свой MIT `LICENSE.txt` (© 2026 Browserbase), в frontmatter ui-test указано `license: MIT`.

Затем дедупликация, нумерация и разбиение на группы.

Итог: тесты, прошло, упало, пропущено, агенты, pass rate. Самодостаточный HTML-отчёт со скриншотами в base64 (до 5 МБ, провалы первыми). - **Минусы:** exploratory намеренно «гуляет» без системы; у маркеров нет severity; axe с CDN; фиксированные ожидания; удалённый режим завязан на Browserbase.
- **Что переиспользовать:**
  - Разделение «координатор планирует (3 раунда) → сабагенты-исполнители с бюджетом шагов и SKIP». Готовый каркас для сотен персона-прогонов.

  - Однострочные маркеры PASS/FAIL, удобные для машинной агрегации.

  - Нейтральная базовая персона рядом с «окрашенными».

### 13. ncklrs/claude-chrome-user-testing

- **Репо:** https://github.com/ncklrs/claude-chrome-user-testing (21★), коммит `be80a88` от 2026-01-07. Лицензия MIT (© 2025 Nick Jensen). Структура: `skills/user-testing/` (SKILL.md, `personas/*.json`, `templates/report.md`), `agents/user-tester/AGENT.md` (≈40 КБ, `model: sonnet`), 10 команд (`/user-test`, `/ab-test`, `/critical-path`, `/smoke-test`, `/wcag-audit` и др.), плюс скиллы form-fuzzer, network-throttling, session-recorder, persona-generator, github-pr.

JSON-схема персоны: techComfort и patience по 1–10, readingSpeed, clickConfidence, тайминги (WPM чтения, задержка клика, пауза растерянности, терпимость к загрузке), frustrationThreshold, триггеры фрустрации, позитивные реакции, типичное поведение, когнитивная нагрузка, связанные критерии WCAG. Есть генератор кастомных персон.

- **Минусы:** тайминги в миллисекундах для LLM-агента условны, потому что сама модель думает секундами; это скорее нарративная рамка. Противоречие Chrome vs Playwright. Последнее обновление в январе 2026.
- **Что переиспользовать:**
  - JSON-схема персоны с измеримыми параметрами терпения и техуровня, триггерами фрустрации и порогом бросания задачи.
  - Метрики сессии: клики, нажатия «назад», самая долгая растерянность.
  - Матрица «проблема × затронутые персоны».
  - Режим `--quiet --output json` для CI.

**Модель агентного цикла** (скрипт `research/scripts/cost.py`):

## Топ-3 для QA одним агентом

1. **vercel-labs/agent-browser `dogfood` + движок agent-browser** (Apache-2.0). Лучший баланс: реальный Chrome, компактные AX-снапшоты, правильные ожидания (`wait --fn`/`--text`, предупреждение про SSE), видео и пошаговые скриншоты, строгий и короткий шаблон отчёта, ≈$0.8 за прогон. ## Лучшие переиспользуемые паттерны (сводно, своими словами)

1. **Repro-first и подбор доказательств под тип бага** (vercel): интерактивный баг — видео плюс шаги со скриншотами, статичный — один кадр. Перед записью воспроизвести повторно.
2. **Persona-lock с детектором дрейфа и обязательный «взгляд новичка»** (jezweb).
3. **Измеримые персоны** (ncklrs): JSON с терпением, техуровнем, триггерами фрустрации и порогом, при котором персона бросает задачу.
4. **Прагматический фильтр персонных жалоб RED/YELLOW/WHITE/GREEN** (hermes adversarial). Без него 1000 персон дадут 1000 шумных тикетов.
5. **Метрики эффективности потока:** клики против оптимума, точки решения, тупики, нажатия «назад», самая долгая растерянность (jezweb + ncklrs). Порог «больше 5 кликов до главной задачи — красный флаг» (hermes).
6. **Interaction Manifest** как доказательство, что агент действительно взаимодействовал, а не только читал (jezweb).
7. **Round-trip A→B→A без перезагрузки** и **клик → сеть → DOM: «ничего не изменилось» = баг** (jezweb).
8. **Матрица «5 состояний × 4 теневых пути»** (идея borghei, только пересказ) и **матрица барьеров «задача × персона»** (designpowers).
9. **Ожидание без networkidle:** `wait --fn`/`wait --text` (agent-browser), `wait_for` по списку текстов и неявное ожидание стабильного DOM (Chrome DevTools MCP), `textGone` (Playwright MCP). Для чата: ждать маркер «стрим завершён», а не тишину сети.
10. **Снапшот в файл, в контекст — только диффы и find** (playwright-cli); скриншоты ограничивать по размеру (DevTools MCP).
11. **Хук ошибок консоли до навигации** (hermes).
12. **Каждую критичную находку превращать в Playwright-тест** (jezweb killer-flows, playwright-cli codegen).
13. **Самокритика и дедупликация находок свежим сабагентом** (KEEP/GENERIC/DUPLICATE) и правило «audit the audit» (jezweb).

## Что придётся дописать самим для генеративного UI в чате

Ни один источник это не покрывает:

- **Детектор окончания стрима.** Атрибут вида `data-streaming="false"` или `aria-busy` на пузыре ответа, `wait --fn` по нему, таймаут со stall-детекцией и отдельная находка «стрим завис». Пример подхода «ждать явный флаг завершения, а не промежуточный DOM»: https://github.com/cacheplane/angular-agent-framework/pull/327/files. Детерминированный мок LLM-бэкенда для повторяемых прогонов: https://dev.classmethod.jp/en/articles/nextjs-llm-streaming-playwright-e2e-without-paid-api/.
- **Инвентарь компонентов внутри сообщения** (карточки, кнопки, слайдеры, формы) после каждого ответа и проверка, что они живые: клик по кнопке в старом сообщении, повторная отправка формы, слайдер после regenerate.
- **Сценарии LLM-нестабильности:** прогнать один и тот же шаг 2–3 раза, потому что ответы недетерминированы; проверить stop, regenerate, частичный ответ, ошибку посреди стрима.
- **Метрики UX чата:** время до первого токена, время до интерактивного компонента, число сообщений до цели. Это аналог «кликов до цели» для разговорного интерфейса.
